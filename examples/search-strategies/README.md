# Deterministic search-strategy example

This example demonstrates the full benchpub flow without making benchpub execute the benchmark.

The benchmark compares two algorithms over the same deterministic workload:

- baseline: linear search;
- treatment: binary search;
- dataset: integers `0..999`;
- 200 deterministic queries generated by `(i * 97) % 1500`;
- metric: number of equality/order comparisons performed.

Wall-clock time is deliberately not used. The example exists to prove evidence flow and reproducibility, not to claim a microbenchmark of Python runtime performance.

## Run

From the repository root:

```bash
python examples/search-strategies/benchmark.py

benchpub validate \
  examples/search-strategies/results/baseline.json \
  examples/search-strategies/results/treatment.json

benchpub compare \
  examples/search-strategies/results/baseline.json \
  examples/search-strategies/results/treatment.json

benchpub render \
  examples/search-strategies/results/baseline.json \
  examples/search-strategies/results/treatment.json \
  --output ./report
```

The expected comparison is compatible because the dataset and declared controlled variables are identical.

The binary-search treatment reduces total comparisons from `132440` to `1846`; `found_queries` remains `135` on both sides.

## Why fixtures are committed

The generated `baseline.json` and `treatment.json` are versioned intentionally.

CI regenerates them and compares the result byte-for-byte. A change to the benchmark or result contract therefore becomes visible instead of silently changing the public example.
